# ممیزی VELNAR SAFEVAULT — ۲۰۲۶/۱۰/۳۱

فاز ۳ نیز انجام شده است: رمزنگاری واقعی کلاینت، API خزانه، CRUD و قفل خودکار.
گزارش اجرا، آزمون‌های بین‌کلاینتی و محدودیت‌های فعلی در `phase3-web-vault.md` است.

این گزارش وضعیت اولیه و فاز ۱ را ثبت می‌کند. فاز ۲ پس از آن انجام شد؛ وضعیت
فعلی احراز هویت، نشست‌ها و محدودسازی ورود در `authentication.md` مستند است.
فایل `backend/.env` اکنون از ردیابی Git خارج شده و نسخهٔ محلی آن حفظ شده است؛
نسخه‌های تاریخی آن هنوز در Git باقی‌اند.

ساختار فایل‌ها، اجزای فرانت‌اند، تنظیمات و مسیرهای Django، ماژول‌های امنیت و
دیتابیس قدیمی، وابستگی‌ها و تست‌ها پیش از تغییر بررسی شدند. فایل‌های باقی‌مانده
از قالب Vite از جمله `App.css` و برخی assetها استفادهٔ فعالی ندارند؛ حذف نشدند.
CLI یک مسیر قدیمی مستقل است و نباید به‌عنوان API وب وارد Django شود.

## فرانت‌اند

React/TypeScript، Vite و Tailwind فعال‌اند. برند و لوگوی VELNAR، داشبورد تیره،
نمای موبایل، جست‌وجو در چهار حساب نمونه، فیلتر Favorites، پنجرهٔ نمایشی افزودن
و بررسی دوره‌ای health وجود دارند. فرم ثبت رمز غیرفعال است. ورود، ثبت‌نام،
ذخیره و ویرایش واقعی، مولد رمز وب، دسته‌ها و تنظیمات حساب پیاده نشده‌اند.
وضعیت Locked و هشدار Preview از قبل به نمایشی‌بودن رابط اشاره می‌کنند.

## بک‌اند و اتصال دیتابیس

پیش از فاز ۱ مدل اختصاصی یا migration خزانه وجود نداشت. فقط `GET /`،
`GET /api/` و `GET /api/health/` ارائه می‌شدند. Health یک liveness ثابت است؛
پاسخ healthy به‌تنهایی اتصال PostgreSQL را ثابت نمی‌کند.

اتصال PostgreSQL با تراکنش read-only جداگانه تأیید شد: نسخهٔ سرور 18.6،
بدون جدول پیش از اجرای فاز ۱. پس از آن migrationهای اولیهٔ Django و چهار مدل
خزانه با موفقیت اعمال شدند. دادهٔ واقعی خزانه یا حساب کاربری ساخته نشد.

`data/vault.db` با اتصال SQLite در حالت read-only بررسی شد: جدول‌های `vault`
و `password` هر دو خالی‌اند. در تعریف قدیمی `created_at` جدول vault غلط املایی
`DEFULT` دیده می‌شود. `backend/db.sqlite3` صفر بایت است. هیچ‌کدام تغییر نکردند.

MySQL در دسترس است، اما تنظیمات فعلی CLI بدون رمز اتصال می‌گیرند و با خطای
1045 / Access denied مواجه می‌شوند. بنابراین schema و تعداد رکوردهای MySQL
تأیید نشده‌اند؛ دربارهٔ نیاز به مهاجرت آن نمی‌توان نتیجه گرفت. محتوای هیچ رمز،
کلید یا رکورد حساس در این ممیزی خوانده یا چاپ نشد.

## امنیت موجود و ضعف‌ها

- CLI رمز حساب را با Fernet رمز می‌کند، اما عنوان، نام کاربری، سایت و یادداشت
  در MySQL متن ساده‌اند. تغییر مشتق‌سازی فعلی بدون مهاجرت کلید، داده‌های قدیمی
  را غیرقابل‌خواندن می‌کند؛ در این فاز حفظ شد.
- مشتق‌سازی کلید و verifier از PBKDF2-SHA256 با ۶۰۰٬۰۰۰ تکرار استفاده می‌کنند؛
  دامنهٔ verifier از کلید جداست. سازگاری با SHA-256 بدون salt برای ورود قدیمی
  باقی است و پس از ورود موفق ارتقا می‌یابد. این معماری Argon2id کلاینت نیست.
- احراز هویت وب، محدودسازی ورود، نشست‌های دستگاه، رمزنگاری کلاینت و API خزانه
  وجود ندارند. middleware استاندارد CSRF و فهرست محدود CORS موجودند؛ امنیت
  کامل نشست، HTTPS و تنظیمات استقرار هنوز تکمیل نشده‌اند.
- `backend/.env` در Git ردیابی می‌شود. `.gitignore` فایل ردیابی‌شده را از تاریخچه
  حذف نمی‌کند. پاک‌سازی ردیابی/تاریخچه و تعویض secretها باید جداگانه انجام شود.
  این فاز فایل محیط یا تاریخچهٔ Git را تغییر نداده است.
- برخی `__pycache__`ها و فایل‌های دیتابیس هم ردیابی می‌شوند؛ پاک‌سازی کنترل‌شده
  لازم است. هیچ فایل قدیمی یا دیتابیسی حذف نشد.

## وابستگی‌ها و سازگاری

محیط backend با Python 3.14.4 اجرا می‌شود و Django 6.1.2، DRF 3.18.3،
psycopg 3.3.6، django-cors-headers 4.9.0 و python-dotenv 1.2.4 دارد.
`pip check` آن خطایی گزارش نکرد. Python پیش‌فرض سیستم 3.12.10 است و نسخه‌های
بسته‌هایش متفاوت‌اند؛ دستورات backend باید با interpreter محیط خودش اجرا شوند.
کتابخانه‌های cryptography و MySQL در Python پیش‌فرض وجود دارند، اما در محیط
backend نصب نیستند؛ این فاز در سرور به آن‌ها احتیاج ندارد.

Node 24.18.0 نصب است و build، lint و هر ۸ تست فرانت‌اند پاس شدند. فایل lock
موجود حفظ شد. Argon2id کلاینت، تست‌بردارهای بین‌کلاینتی و کتابخانه/سازوکار
محدودسازی ورود هنوز انتخاب و اضافه نشده‌اند. نصب بستهٔ سروری Argon2 به‌تنهایی
رمزنگاری کلاینت ایجاد نمی‌کند.

## معماری و برنامهٔ مرحله‌ای

۱. **زیرساخت بک‌اند و مدل‌ها — انجام شد:** حفظ User استاندارد Django و sessions،
مدل Vault با مالک مشخص و پروفایل ثابت نسخهٔ ۱، VaultEntry با payload کاملاً
رمزشده، SecuritySettings و جدول رزرو nonce. سرویس‌ها کنترل مالکیت، تراکنش،
قفل سطر و کنترل revision دارند. مجوز پیش‌فرض DRF احراز هویت است؛ endpoint
نوشتنی هنوز ارائه نمی‌شود. قالب در `encryption-format.md` مستند شده است.

۲. **هویت و نشست:** ثبت‌نام و ورود مستقل از master password خزانه، خروج و
مدیریت نشست، سیاست credential و بازیابی حساب، CSRF، cookie امن، CORS مبتنی بر
محیط، محدودسازی واقعی تلاش‌های ورود و تست‌های دسترسی افقی. ثبت بدنهٔ درخواست‌های
حساس ممنوع است. بازیابی حساب نباید به‌اشتباه بازیابی کلید خزانه معرفی شود.

۳. **کلاینت و API خزانه:** Argon2id واقعی با کتابخانهٔ بررسی‌شده در worker،
AES-256-GCM با Web Crypto، تست‌بردار مشترک، آزمون دستکاری/AAD و کلید اشتباه،
کلیدها فقط در حافظه، serializers و API متصل به سرویس‌ها، سپس اتصال تدریجی
فرم‌های موجود، ویرایش، مولد، جست‌وجو، دسته‌ها و Favorites در کلاینت.

۴. **همگام‌سازی و عرضه:** سیاست تعارض و حذف برای sync، ذخیرهٔ آفلاین رمز‌شده،
خروج و قفل خودکار واقعی، پشتیبان‌گیری، تنظیمات استقرار، تست نفوذ و ممیزی مستقل؛
سپس ارزیابی کلاینت‌های Windows و موبایل بر پایهٔ همین قرارداد.

## اعتبارسنجی انجام‌شده

- بک‌اند: ۲۳ تست روی PostgreSQL مستقل موقت پاس شدند، شامل رقابت دو اتصال برای
  ویرایش یک revision. دیتابیس آزمایشی پس از اجرا حذف شد؛ از safevault برای
  داده‌های تست استفاده نشد.
- SQLite در حافظه: ۲۲ تست پاس شد و آزمون قفل PostgreSQL به‌درستی skip شد.
- CLI: ۲۸ تست پاس شد؛ تست یکپارچهٔ MySQL طبق تنظیم قبلی opt-in و skip بود.
- فرانت‌اند: ۸ تست، build و lint پاس شدند.
- مدل‌ها و migration همگام‌اند و بررسی Django خطایی گزارش نکرد.

این نتایج صرفاً زیرساخت و رفتار فعلی را پوشش می‌دهند؛ تأیید امنیت محصول نهایی
یا پیاده‌سازی رمزنگاری کلاینت نیستند.
